# 大棚经济层：用 Mesa 做竞价原型

物理层回答「这块地能长出多少」，这一层回答「为了长出这些，花了多少、花在谁身上」。

目标不是给出一套能直接报给银行的成本表，而是先回答一个可证伪的问题：

> 同一座棚、同一份气象、同一套电价下，把**独享容量**换成**共享容量**，
> 不同作物会不会拿到**不同**的单位成本曲线？差异是竞争造成的，还是天气或电价造成的？

如果答案是「会，且能归因到竞争」，把 CropForge 的产量接进来才有意义。
这个原型就是为这一步做的。代码在 `rancho/econ/`。

> **版本与口径。** 本文全部数值基于当前 `MODEL_VERSION = 2`，用
> `uv run rancho econ --out-dir runs/econ` 重跑得到，与 README 的当期对照表同源。
> v2 的口径是：FAO-56 水分胁迫系数 `Ks` 分母为 `(1−p)·(FC−WP)`；可售鲜重
> `fresh_per_dry = 收获指数 × 商品率 ÷ 干物质率`，物理层与经济层共用同一份
> `rancho/crops/*.toml` 参数；温控改在 **kW_e 空间**按各作物当小时的实际 COP 清算，
> 泵耗也占电网容量；`run_id` 折入模板摘要与模型版本。
>
> 改模板会自动失效缓存；改农艺/经济公式、气候生成或升级 CropForge，必须先把
> `rancho/frames.py` 的 `MODEL_VERSION` 加一，再重跑本文全部数字，否则会静默命中旧结果。
> 版本定义与重跑契约见 README 的「缓存与模型版本」。

## 双层结构

```text
CropForge · 物理层（逐日）                Mesa · 经济层（逐小时）
───────────────────────────              ──────────────────────────
辐射截获 → 干物质增量 ────── 产量 ──────►  作物 Agent 的边际价值报价
根区水量平衡 → Ks        ────── 胁迫 ────►        │
氮素矿化 / 吸收 → Kn                      大棚 Agent 按价值降序清算
                                                   │
                                        成本账本 → 日成本 / 单位成本
```

上半行（辐射截获 → 干物质）有三套实现，产量函数统一在 `LightResponse` 协议下：

| `--growth`  | 产量从哪来                                            | 边际值从哪来                  |
| ----------- | ----------------------------------------------------- | ----------------------------- |
| `analytic`  | `growth_max × DLI/(DLI+K)`，第 1 天就当满冠层         | 解析导数，随缺口收窄          |
| `cropforge` | `rancho.vegetables` 的插件 + Beer-Lambert 截获        | 对 DLI 差分，冠层固定时是常数 |
| `farm`      | 真跑一次 CropForge 农场（6×6 田、辐射钩子、逐日引擎） | 整季 ±10 % 光照重跑后逐日差分 |

三套后端最终都把干物质折成**同一口径的可售鲜重**：乘 `fresh_per_dry`，而不是简单除以
干物质率。这一点由 `agronomy.py` 与 `econ/spec.py` 共用，避免物理层与经济层各算一套。

三者的差别不只是数值——解析式在边际上饱和，插件与农场在固定冠层下是线性的，
这决定了报价随缺口收窄还是不变。下半行（报价、清算、账本、判据）对三者一视同仁。
`farm` 还要跟市场来回迭代，见文末「第三阶段」。

## 一小时里发生了什么

`GreenhouseAgent.step()` 逐小时推进，24 步为一天：

| 步骤 | 谁   | 内容                                                                                                   |
| ---- | ---- | ------------------------------------------------------------------------------------------------------ |
| 1    | 大棚 | 读外生序列：室外气温、棚内辐射、分时电价、水价、肥料价；算被动棚温 `T_passive = T_out + min(9, 4.6·R)` |
| 2    | 作物 | 把这一小时的自然光记进当日 DLI                                                                         |
| 3    | 大棚 | 清算**温控**：申报是 kW_th，先按各作物当小时 COP 折成 kW_e，在 `min(35.2, 20/3.2)` kW_e 里竞价，再按 20 kW_th 热装机裁剪 |
| 4    | 大棚 | 清算**补光**：申报量对 `36 kW − 待机 0.8 kW − 温控已占电力`                                            |
| 5    | 作物 | 记账：交付的冷热量、电费、耗水、达到的棚温、品质损伤                                                   |
| 6    | 大棚 | 06:00 清算**灌溉水**与**肥料**（一天一次，日需求在此时确定）；泵耗 `0.35 kWh/m³` 也占第 4 步剩下的电网容量 |
| 7    | 大棚 | 23:00 日结算：算生长量、扣土壤水、结氮平衡、写一行 `DayRecord`                                         |

第 3 步先于第 4 步是有意的：温控防的是不可逆的品质损伤，补光只加产量。
电力预算先满足冷热，剩下多少再给灯。当前电价下这一步几乎不产生决策——
三作物 28 天的补光采购都是 0 kWh，见「为什么是逐小时」。

## 四种资源，四套清算规则

| 资源    | 容量                 | 清算时点         | 作物按什么报价                                          | 保留价         |
| ------- | -------------------- | ---------------- | ------------------------------------------------------- | -------------- |
| 冷 / 热 | 20 kW_th / 36 kW_e   | 每小时，先于补光 | 这一步买到的温度因子增益 × 可售产量，加上避免的品质损失 | `tariff / COP` |
| 补光电  | 36 kW 扣除待机与温控 | 每小时，后于冷热 | `dg/dDLI × 10.8 mol/kWh × 售价 × 胁迫`                  | `tariff`       |
| 灌溉水  | 1.4 m³/日            | 每日 06:00       | 缓解 Ks 亏缺换来的产量增益                              | 无             |
| 肥料    | 2.0 kg/日            | 每日 06:00       | 氮响应的边际产量增益（Mitscherlich）                    | `fert_price`   |

保留价的意思是「低于这个价我宁可不买」：冷热按 `tariff/COP` 折成每 kWh_th 的成本，
补光就是电价本身。灌溉**没有**保留价——种植者不会为了省 4 元/m³ 让一畦菜蔫掉，
所以整份需求都报上去，井的出水量决定能浇多少。v2 里灌溉正是最紧的那一个。

## 为什么是逐小时

按日均电价会把这一层最重要的一次决策抹平。但换成萨尔瓦多真实电价之后，这一节要回答的
问题变了：不再是「谷段便宜时买多少」，而是「这个电价下还买不买得起」。

### 电价的来源

两套费率都取自 **AES CLESA 面向终端用户的费率表**（DGEHM 决议 No. 97/2026/DE、
98/2026/DE，2026 年 8 月 1 日起执行），中等需求档（10–50 kW，与棚里 36 kW 的进线
对应）、低压（BT）：

| 情景         | 计量方式 | Punta 峰 | Resto 平 | Valle 谷 |
| ------------ | -------- | -------- | -------- | -------- |
| `sv_horaria` | 按小时   | 0.209986 | 0.178033 | 0.206997 |
| `sv_plana`   | 按功率   | 0.186401 | 0.186401 | 0.186401 |

单位 USD/kWh。萨尔瓦多自 2001 年起美元化，费率以美元公布，所以电价**按原值入库**，
只在取价时乘 `TariffSpec.fx` 折算成记账币种（CNY，当前取 6.6723）。保留原值是为了让
费率表能对着原始出处核——换算过的数字没法核对。

两个情景的差别不是贵贱，而是**分不分时**：分时计量给了负荷搬移的空间，统一费率没有。

### 一个反直觉的地方

表里 `Valle`（谷）比 `Resto`（平）**贵**（0.207 vs 0.178）。这不是抄串了行，PDF
原始表格里 BT 和 MT 两档都这个顺序。原因是光伏：萨尔瓦多 2025 年底装了 846 MW，
白天出力把中间时段的电价压了下去，日落后光伏归零、由地热和水电顶夜班，反而更贵。
习惯了中国农业峰谷电价的人——那边谷段是账单上最便宜的一档，灯都排夜里开——
到这里得先把这个直觉倒过来。

### 结果：补光一度都没买

28 天 672 小时，两个情景下三个作物的补光采购量**都是 0 kWh**。棚内 DLI 均值
11.32 mol/m²/d，番茄目标 20，缺口看着很大，但按当前可售鲜重口径折回去，
补光换来的边际产量撑不住这个电价。

扫一遍就知道门槛在哪（三作物共享臂、热带站点、28 天；把统一费率整体改价）：

| 电价（USD/kWh） | 折元/kWh | 补光采购  |
| --------------- | -------- | --------- |
| 0.010           | 0.067    | 4017 kWh  |
| 0.020           | 0.133    | 456 kWh   |
| 0.030           | 0.200    | 0 kWh     |
| 0.040           | 0.267    | 0 kWh     |
| 0.060           | 0.400    | 0 kWh     |

补光在 **0.02–0.03 USD/kWh** 之间退出市场，而萨尔瓦多零售电价（0.178–0.210）是
这个门槛的 **6–10 倍**，中间没有可调度空间。这也解释了为什么两套情景跑出来
几乎一样（单位成本极差都是 10.1 %）——需要搬的负荷根本不存在。

想让补光重新进入决策，只有两条路：电价降到 0.03 USD/kWh 以下，或者自己发电。后者在
萨尔瓦多是有法律依据的——2025 年第 436 号法令（《可再生能源利用促进法》）与 2026 年
SIGET 第 072-E-2026 号实施细则，允许自发自用、余电上网按净计费补偿，配套储能同样
享受 10 年税收优惠。中美洲工商业屋顶光伏 2026 年的平准化成本约 0.03–0.09 USD/kWh，
**正好压在补光的盈亏平衡线附近**，所以那才是真正值得做的第二个情景。

## 报价是边际的，不是平均的

每份申报拆成 3 步（`THERMAL_STEPS`），每步按它实际买到的那一段温度区间定价。
响应是凹的，所以第一步最贵、最后一步最便宜；清算价因此落在某个作物**申报区间内部**，
而不是在它的边界上一刀切。这一步的方法在 v2 没有变，变的是约束落在哪个资源上。

当前口径下温控几乎不拥挤：672 小时里只有 **5 小时**申报超过 20 kW_th 热装机，
全部集中在第 27 天 11:00–15:00，峰值 36.29 kW_th，清算影子价最高
0.340 元/kWh_th。真正稀缺的是 06:00 的灌溉清算——全屋灌溉逾配 11.41 %，
高于温控的 7.31 %，补光与肥料都是 0 %。

四资源各自清算、各自记账，因此「谁被挤掉」要分开看：

| 作物 | 温控被拒 kWh_th | 灌溉被拒 m³ | 该作物最紧资源逾配率 |
| ---- | --------------- | ----------- | -------------------- |
| 番茄 | 4.82            | 3.972       | 25.3 %               |
| 黄瓜 | 28.71           | 0.000       | 25.7 %               |
| 生菜 | 12.88           | 0.215       | 2.6 %                |

判据里的 `binding_crop` 是黄瓜（25.7 %，来自**温控**口径），而产量掉得最狠的是
番茄（−12.9 %，来自**灌溉**口径：全屋 4.187 m³ 水缺口里它占 95 %）。
两个数字不矛盾，但也不是同一件事：它们分别描述电热与水的稀缺。读结论时必须带上看的是哪个资源，
这也是「已知局限」第 5 条要处理的问题。

## 三臂对照

只跑一个「共享」臂，看到差异也无法排除「天气或电价就是那样」。所以同一份 forcing 跑三遍：

| 臂       | 容量               | 回答什么                               |
| -------- | ------------------ | -------------------------------------- |
| `solo`   | ×10⁴（等于无约束） | 每个作物独占整座棚时会买什么、成本多少 |
| `pooled` | 实际容量           | 三个作物互相竞价时各自拿到什么         |
| `null`   | ×10³               | 分配器本身有没有偏                     |

`null` 是自检：容量放大一千倍，结果必须与 `solo` **逐位一致**。不一致说明清算逻辑
在无约束时也在改变分配，后面所有对比都不成立。实测 `null_gap = 0.0`。

三臂共用同一份 `Forcing`（同 seed 一次生成），因而不存在"天气不一样"的解释。
当前基线：solo 107.30 kg / 1025.49 元，pooled 102.78 kg / 994.52 元，null 与 solo 逐位相同。

## 判据

| 判据                      | 阈值   | 含义                           |
| ------------------------- | ------ | ------------------------------ |
| `null_gap`                | ≤ 1e-9 | 分配器无偏                     |
| 最紧作物逾配率 `pressure` | > 5 %  | 容量确实紧，竞争真的发生了     |
| 单位成本变动极差 `spread` | > 2 %  | 各作物不是按比例被砍           |
| 秩相关 `rho`              | 报告值 | 超配份额与成本变动的方向一致性 |

`pressure` 取**最紧的那个作物**而不是全棚平均，并且按资源分别计算：温控（kWh_th）、
补光（kWh_e）、灌溉（m³）、肥料（kg）各有自己的 `没拿到 / (没拿到 + 拿到)`，作物取四者
最大值，全棚另报最紧资源的平均逾配。按量而不按钱算，也不再把 kWh_th 与 kWh_e 相加——
否则收紧一口井时，缺口会被宽松的电网掩盖。全棚平均会把一畦饿着的菜藏在两个吃饱的后面，
而「是否有个别作物被系统性挤掉」正是要看的现象。

绝收作物（任一侧产量为零）的 `comparable = False`：它没有单位成本，会被排除在
`spread` 与 `rho` 之外，报告里显示「—」而不是 `0 元/kg`。

## 测试

`uv run pytest` 跑全部 209 个用例，十几秒，不联网。`test_econ_farm.py` 是例外：它的每个用例都在
真跑农场季运行（一次约 0.01 秒），所以响应表按模块建一次、用前复制——否则光这一组就要几十秒。

| 文件                    | 守什么                                                                         |
| ----------------------- | ------------------------------------------------------------------------------ |
| `test_econ_market.py`   | 序贯配置的守恒、容量上限、并列排序与确定性；逾配按作物的**整条报价曲线**汇总   |
| `test_econ_verdict.py`  | 三臂判据的每个阈值各配一个刚好落在失败侧的例子                                 |
| `test_econ_forcing.py`  | 电价形状、日光窗口、同种子可复现、水价不越基准 ±10 %                           |
| `test_econ_run.py`      | 短窗口实跑：容量不被突破、交付不超申报、累计成本与日增量对得上；Ks 与鲜重折算口径 |
| `test_econ_growth.py`   | 两套产量函数：解析式的导数、CropForge 的单调性与差分导数、冠层随热时间张开     |
| `test_econ_farm.py`     | 真实农场季：定植起步、光照单调、响应表的锚点与钳位、日期游标隔离、两套后端一致 |
| `test_econ_report.py`   | HTML 报告：颜色按指标方向、常量域坐标轴、方法说明随后端切换、零产量显示「—」    |

三条回归对应已经修过的 bug，测试锁的是它们的失败形态：

- **逾配必须按整条曲线算。** 一个作物对同一资源报三步，`served` 是三步累计；若从按作物
  建索引的 dict 里取单步来比，被砍掉大半的作物会报成零缺口。
  `test_denial_is_measured_across_a_crops_whole_step_curve` 用一份只有第一步成交的报价锁住它。
- **日成本是增量，不是累计。** `DayRecord` 的成本列若填了累计值，第二天的行会把第一天
  的电费再算一遍，而总量看上去仍然「对」。`test_cumulative_cost_is_monotone_and_matches_its_daily_increment`
  验的是「累计差 = 当日分项和」。
- **定植起点不能省。** 农场季从 CropForge 的播种状态起步，第 1 天 LAI 只有 0.03，4 天产量
  只有插件后端的 1/16。`test_the_season_starts_from_a_transplanted_seedling` 断言第 1 天就
  有产量，`test_the_farm_and_the_plugin_backends_agree_on_the_same_season` 断言两套后端在
  2 % 以内——把 `_seed_seedlings` 删掉，这两条同时红。

判据阈值 `NULL_TOLERANCE` / `MIN_PRESSURE` / `MIN_UNIT_SHIFT` 从 `probe.py` 直接导入测试，
改阈值会连带改到边界用例——这是有意的，阈值与它的证据不该分家。

## 参数从哪来

价格与容量集中在 `spec.py` 的四个 dataclass 里，单位写在字段名上。作物本身的参数**不复制**：

| 参数                                                                 | 来源                                        |
| -------------------------------------------------------------------- | ------------------------------------------- |
| `root_zone_mm` / `kc_mid` / `depletion_fraction` / `n_concentration` | 模板 `[water]` → `agronomy.CROP_WATER`      |
| `fresh_per_dry`（含 `dry_matter_fraction`、收获指数、商品率）        | 模板 `[product]` → `scenario.CROP_PROFILES` |
| 售价、DLI 目标、温控设定点、基数温度、生长上限、`transplant_lai`     | 模板 `[market]` / `[growth]`                |
| 面积与土壤初值（面积、起始含氮量、田间持水量、凋萎点）               | `econ/spec.py`                              |

前三项都在 `rancho/crops/<作物>.toml` 里，改动一处两层的口径就一起变。最后一项不是作物属性——
三畦菜共用一个棚，但各畦面积与起手土壤是场地参数，所以仍留在经济层。

两层共用同一份水肥系数与同一条 `water_stress_ks()`，因此不会出现「经济层按 450 mm 根区收费、
物理层按 300 mm 耗水」这种漂移。这也是第二阶段能对接的前提。没有 `[market]` 段的作物（谷物）
无法定价，`econ.spec._crop` 会直接报出是哪个作物缺了哪一段。

## 结果（萨尔瓦多高原 · 28 天 · seed 42）

气象：均温 23.14 ℃（17.3–28.94），棚内 DLI 均值 11.32 mol/m²/d；电价均值
**1.287 元/kWh**（1.035–1.598，折 0.1933 USD/kWh 均值），水价 3.80 元/m³，
肥料 5.21 元/kg。三套产量来源跑同一份 forcing、同一个种子：
`analytic` 是第一阶段的饱和光响应代理，`cropforge` 是第二阶段的插件 + Beer-Lambert 截获，
`farm` 是第三阶段的真实农场季。

### 主对照表

表内是**共享臂相对独享臂**的单位成本变动；极差为三作物最大差。六组全部通过判据，
`null_gap = 0`。

| 产量来源    | 情景         | 番茄    | 黄瓜   | 生菜   | 极差   | 最紧作物逾配 | 全屋平均 | 秩相关 |
| ----------- | ------------ | ------- | ------ | ------ | ------ | ------------ | -------- | ------ |

281.22 kg 对 107.30 kg），报价与逾配率也跟着变。

### `cropforge` 与 `analytic` 差在哪

三条，按影响从大到小（`farm` 与 `cropforge` 同源，不参与这一节的对比）：

1. **冠层是状态，不是常数。** `analytic` 的 `growth_max` 是「满冠层潜在值」，第 1 天就成立；
   `cropforge` 从定植 LAI 0.45–0.75 起步，靠热时间把冠层张开到 2.1–2.2，28 天里产量先低后高。
2. **对光是线性还是饱和。** 固定冠层下 Beer-Lambert 对入射辐射是线性的，每多一 mol 值同样多的克数；
   饱和响应则越补越不值。于是补光报价不再随缺口收窄——竞争更像「价格门槛」而不是「平滑分配」。
   当前电价下两套后端的补光成交量**都是 0 kWh**，差别要到 0.03 USD/kWh 以下才显形。
3. **温度对产量的作用变小。** CropForge 的插件只用温度算热时间（发育与冠层），不用它算光合，
   温度对当天产量的影响只剩本层补的三角响应。`analytic` 下黄瓜丢配额时产量掉得更快
   （−19.4 %），单位成本反而升 +2.8 %；`cropforge` 下只掉 −1.2 %。

## 为什么是番茄

共享臂里受损最重的是**番茄**：单位成本 12.76 → 13.87 元/kg（+8.7 %），
产量 27.37 → 23.85 kg（−12.9 %），毛利 33.9 → 3.0 元（−91.1 %），几乎被打到盈亏线。

原因是水，不是电。共享灌溉容量 1.4 m³/日，全季被拒 4.187 m³，其中番茄占
3.972 m³（95 %）；黄瓜与生菜的水需求基本被满足。灌溉按边际价值排序，
番茄在这次分配里排在后面，而 `water_stress_ks()` 按 `(1−p)·(FC−WP)` 计算，
根区含水量一旦跌进允许消耗区间，`Ks` 就快速下滑，减产一路传到单位成本上。

对比之下黄瓜几乎不动：单位成本 5.38 → 5.31 元/kg（−1.4 %），毛利还从 210.6 涨到
212.6 元。它在**温控**口径上是被拒最多的作物（28.71 kWh_th，判据因此把它报成
`binding_crop`），但温控在当前基线里不是最紧资源，丢掉的冷量没有转化成产量损失。
这正是「按四资源分别记账」之后出现的新结论：**申报被拒最多的作物，不一定是最后受损最重的作物。**

所以「边际生产者」这个说法在当前口径下要拆开讲：按电热排序，黄瓜垫底；
按最终经济结果，番茄才是被共享容量挤到亏损边缘的那一个。

## 已知局限

1. **产量来源有三档，最高一档仍不是完整的 CropForge 场景**。`farm` 会真跑网格与引擎，
   但田只有 6×6 格（只为让物理钩子有地方写）、没有地形与风、没有接管逐日 Parquet 日志，
   也没有开 CropForge 自己的水分桶（本层仍用 FAO-56 单层桶）。病害引擎虽然能开，但蔬菜插件
   不读 `plant.custom['disease_state']`，开了也只是空转，所以没接。产量按折鲜重的市场可售量
   记账，不用于报产。
2. **作物是短视的**。只看今天的价格和状态，不做跨日套利，也不补前一天的欠账。
3. **棚温是集总系数**。`T_passive = T_out + 4.6·R`（上限 +9 K）、`ΔT = Q/(UA·A)`，
   没有热惯性、没有显热/潜热分离、没有通风。
4. **ET₀ 是辐射代理式**（`0.28·R + 0.06·(T−15)`），与物理层的 Penman-Monteith 不同口径。
5. **`denied_share` 与秩相关仍只覆盖电热**。`pressure` 已按四资源分别计算，但
   `denied_share` / `rho` / summary 里的「占缺口」仍按温控 + 补光分摊，
   不反映水肥缺口；`kwh_hvac_denied` 是 kWh_th，而 `kwh_hvac` 是 kWh_e，量纲不同。
   因此本文凡涉及「占比」的数字都要按电热口径读。
6. **电力空间的报价排序未按 COP 换算价值**。`_clear_thermal` 把申报量除以 COP 换成 kW_e，
   但报价 `value` 仍是元/kWh_th；竞价按「每 kWh_th 的价值」排序，而电网被占用的是 kW_e。
   COP 分散时（不同作物设定点不同）merit order 会偏离「每度电价值最高者优先」。
   默认基线多为制冷、COP 接近，影响尚未在结果里显形，但换站点或改设定点前应先修。
7. **绝收与单作物的边界语义未完全统一**。绝收作物已标为不可比、报告显示「—」，
   但 `delta_yield` 在独享臂产量为零时仍显示 `+0.0 %`；单个作物或全部绝收时
   `spread` 恒为 0，判据会给出「按比例分摊」的误导文案。
8. **零产量单位成本在三份产物里表示不一致**：`probe.json` 为 `null`、HTML 为「—」、
   `daily.csv` 仍写 `0.0`。
9. **多电价时只保留最后一份耦合记录**。`ProbeResult.coupling` 是顶层单 dict，
   跑两个 tariff 时前一个情景的迭代轮数与残差不可审计。
10. **容量是外生的**，没有投资决策；不含折旧、人工、种苗、采后，
    `overhead_yuan_m2_day` 默认为 0，只摊待机电费。
11. **单棚三作物**，没有多棚、没有共享水源或共用采后线，Mesa 的空间模块未启用。

## 第二阶段：接 CropForge

接入点只有「产量怎么来」这一件事，报价、清算、账本、判据都没动。`rancho.econ.growth`
把产量函数抽成 `LightResponse` 协议，两套实现：

| 环节       | 做法                                                                                                        |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| 冠层与物候 | 直接实例化 `rancho.vegetables` 的插件（`Tomato` / `Cucumber` / `Lettuce`），每天喂一次当天的 DLI 与棚内均温 |
| 截获       | `cropforge.physics.radiation.calculate_intercepted_par`：`PAR_int = 太阳辐射 × 0.5 × (1 − e^{−k·LAI})`      |
| 干物质     | `RUE × PAR_int`，再乘 `fresh_per_dry` 折成**可售鲜重**（收获指数 × 商品率 ÷ 干物质率）                      |
| 边际值     | 对 DLI 做中心差分（步长 0.5 %），不手抄 CropForge 内部的 PAR 系数                                           |
| 留在本层   | 三角温度响应、`Ks` / `Kn`、品质损伤、全部成本记账                                                           |

两处刻意的取舍：

1. **应力只算一次。** 引擎里 `adjust_canopy` 会按供水缩冠层，插件又乘一次 `Ks·Kn`——渲染上没问题，
   在经济探针里会把减产放大一倍。这里冠层走潜在曲线，应力只从产量那一侧进。
2. **温度只进热时间。** CropForge 的蔬菜插件没有「高温抑制光合」的项，本层保留三角响应补这个缺口。

接上之后暴露两个问题，都是第一阶段的代理掩盖住的：

- **潜在产量随冠层走，不再随 DLI 走。** `growth_max` 取的是「满冠层、最优温度」的潜在值，
  第 1 天就成立；插件从定植 LAI 0.45–0.75 起步，28 天只张到 2.1–2.2。
  独享臂总产量因此从 `analytic` 的 281.22 kg 降到 107.30 kg，单位成本整体抬高。
- **损伤按一天计价会引发死亡螺旋。** 原来的损坏项是 `损伤速率 × 当日产值`，生菜据此判断
  「不值得为降温花钱」，于是不买冷、品质掉到 0.01、产量归零、报价更低——一路下坠。
  损伤不可逆，正确口径是**剩余全季的产量**；改成 `损伤速率 × 当日产值 × 剩余天数` 后生菜才恢复理性。

还留在外面的是 CropForge 的网格、物理引擎与逐日 Parquet 状态日志。这件事在第三阶段做了。

## 第三阶段：让经济层驱动整座农场

第二阶段仍然是「调插件的函数」：一个植株、没有田、没有物理钩子、没有引擎的时间步循环。
第三阶段把 `Farm` 真的跑起来——每个作物一座 `6 × 6` 的田，CropForge 负责时间步、辐射钩子
与插件调度，经济层从运行中的植株上读回逐日干物质。

### 为什么必须迭代

市场在买光之前就要知道「多一 mol 值多少钱」，而这个价钱要等收获才存在。两个方向接不上，
只能交替：

```text
       ┌────────────────────────────────────────────────────┐
       │                                                    │
  市场清算（逐小时）──► 交付的 DLI / 棚温 ──► 农场季运行（逐日）
       │                                                    │
       └───────── 逐日干物质增量 → 响应表 ◄──────────────────┘
```

第一轮没有响应表可用，就从插件后端起步——也就是第二阶段的答案，同时是一个真实种植者会用的
初始猜测。之后每一轮都拿上一轮市场**真正交付**的逐日光量跑一次农场，把测到的响应表喂回去。
总产量相对变化小于 1 % 就停；**首轮只是初值，不得判收敛**，所以 Farm 模式至少需要两轮，
CLI 会拒绝 `--farm-passes 1`。当前基线两轮即停，残差 `1e-05`（0.001 %）。

### 边际价值是测出来的，不是推出来的

同一季跑三遍：光照 ×1、×1.1、×0.9，逐日干物质增量做中心差分：

```python
slope[d] = (DM_up[d] - DM_down[d]) * fresh_per_dry / (0.2 * DLI_ref[d])
```

报价用的斜率因此是物理层自己的量，而不是本层手抄的一条导数公式。响应表是**分段线性**的：
每天一个锚点（基准季的实际产量）加一个斜率，评价别的光量就在锚点上外插。

有一个前提值得写下来：冠层在这里只由热时间驱动，生物量也不反馈到截获，所以三次运行的冠层
轨迹完全相同，季级扰动在这套方程里就等于逐日的偏导。若换成一个「光照影响张叶」的插件，
同样的差分测到的是**全导数**——它高估当天这一 mol 的边际值，因为多出来的光把后面几天的冠层
也改了。

### 三个踩到才会发现的坑

| 坑                 | 症状                                      | 处理                                                                                            |
| ------------------ | ----------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 从播种起步         | 第 1 天 LAI 0.03，4 天产量只有插件的 1/16 | 初始化田间状态时按定植苗设 LAI 与热时间。负相位归物理引擎，这是唯一能赶在第一次辐射钩子之前的缝 |
| 响应表被两个臂共享 | `null_gap = 8.4 %`，自检直接判红          | 表带日期游标，每次取用复制一份：`replace(table, day=0)`                                         |
| 应力算两遍         | 一接进来产量就比插件低一个 `Ks·Kn`        | 物理侧钉住 `Ks = Kn = 1`，与插件后端同一条规矩：应力只由收货的那一层算一次                      |

### 结果：与前两个阶段互相印证

`--growth farm` 用同一份 forcing、同一个种子跑 28 天：

| 臂 / 作物     | `cropforge`           | `farm`                | 差      |
| ------------- | --------------------- | --------------------- | ------- |
| 独享 · 番茄   | 27.37 kg / 349.31 元  | 27.37 kg / 349.31 元  | 0       |
| 独享 · 黄瓜   | 58.26 kg / 313.74 元  | 58.27 kg / 313.74 元  | < 0.01 kg |
| 独享 · 生菜   | 21.67 kg / 362.45 元  | 21.67 kg / 362.45 元  | 0       |
| 共享 · 三作物 | 102.78 kg / 994.52 元 | 102.78 kg / 994.52 元 | 0       |
| `analytic` 对照 | 281.22 kg / 1489.16 元 | —                   | 代理口径，不同档 |

判据一模一样：`null_gap = 0`、最紧作物逾配 25.7 %、极差 10.1 %、秩相关 −1.00。
**「几乎没变」不是白跑**：它说明用插件算出来的产量，与引擎逐日跑出来的是同一件事，
第二阶段那些数字不是调出来的。工程上换来的是，产量路径现在走 `Farm.run()`——网格、
物理钩子、逐日状态日志都在引擎手里，换插件、加引擎、改种植密度都只影响这一层。

代价：28 天三作物、两轮、两个电价情景，共 36 次农场季运行，约 0.7 秒（单次约 0.01 秒）。
比插件后端慢约 5 倍，仍在「改一次参数就能重跑」的量级。

**省掉的日志。** 这一层有个不体面的开销：`Farm.run()` 无条件把整田逐日状态编码成
分区 Parquet，而探针一个字节都不读，读完就删。所以 `cropforge_acl._Unlogged` 在跑季运行期间把
`StateLogger` 的 `record`/`flush` 换成空实现：其余一切照旧（会话目录、`log_path`、地形转储都还在），
只是不再落盘。这是对 CropForge 内部的临时接管，不是它支持的开关；数值逐位不变（A/B 对照过）。

## 命令行与产物

```bash

uv run rancho econ --tariff sv_horaria --days 60 --no-open  # 只跑一种电价，不弹浏览器

```

电价情景只有 `sv_horaria` / `sv_plana` 两个；`farm` 是 `--growth` 的取值，不是电价。
产物落在 `runs/econ/<run-id>/`：

| 文件          | 内容                                                                                                                     |

| `daily.csv`   | regime × arm × crop × day 的扁平行（32 列），可直接进 pandas                                                             |
| `report.html` | 自包含报告：气温包络、逐小时电价、累计成本曲线（solo 虚线 vs pooled 实线）、单位成本曲线、成本构成、逐作物对照、稀缺时刻 |

HTML 内联 CSS 与 SVG，无 CDN、无 JavaScript，五年后打开仍能读。
`run-id` 由站点、天数、种子、情景列表、产量来源与迭代轮数哈希而来，同参数重跑落到同一目录、
数字逐位一致。`probe.json` 的 `coupling` 字段记录迭代轮数与残差，报告头部会多一个「双层迭代」标签；
跑多个电价时该字段只保留最后一个情景的记录，见「已知局限」第 9 条。
